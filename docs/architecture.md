# معماری — TechFlow

## نمای کلی

```
┌────────────────────────────┐        ┌─────────────────────────────────────────┐
│  React 18 + Vite (5173)    │  JSON  │  Django 5 + DRF (8000)                 │
│  SPA، RTL فارسی، Session  │◄──────►│  REST API  /api/*                      │
│  Cookie + CSRF Token       │ proxy  │  RBAC در لایه View + Serializer        │
└────────────────────────────┘        │  Signals: audit + risk                 │
                                       │  Services: dashboards, risk, report   │
                                       └───────────────┬───────────────────────┘
                                                       │
                                          ┌────────────▼────────────┐
                                          │  PostgreSQL 15 (Docker) │
                                          └─────────────────────────┘
```

**تصمیم بزرگ**: مونولیت ماژولار (modular monolith). در این مقیاس (۱–۳ تیم، < ۵۰ کاربر)
میکروسرویس هزینه بدون فایده است؛ ماژول‌های Django با مرز واضح، هم تمیزی کد را نگه می‌دارند
و هم امکان جداسازی آتی را حفظ می‌کنند.

## لایه‌ها

### ۱. Backend — ۱۰ اپلیکیشن Django

| اپ                      | مسئولیت                                                                                                                                           | مدل‌ها                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |

| `organizations`         | مرز چندسازمانی (ال‌ف: یک سازمان)                                                                                                                  | `Organization`                                                                  |

### ۲. موتور ریسک (شفاف و قابل‌اعتماد)

`dashboards/risk.py` برای هر پروژه **بدون مدل و بدون قضاوت**، سه سیگنال محاسبه می‌کند:

| سیگنال           | شرط                                             | نتیجه                   |
| ---------------- | ----------------------------------------------- | ----------------------- |
| مانع باز         | `blockers(status=open).count() > 0`             | `risk_status = blocked` |
| مهلت نزدیک       | `0 <= days_to_expected <= 14` و `progress < 70` | `at_risk`               |
| مهلت گذشته       | `days_to_expected < 0` و وضعیت ≠ done/cancelled | `at_risk`               |
| به‌روزرسانی ضعیف | `updated_at` > ۷ روز و وضعیت فعال               | `stale` (نمایش جداگانه) |
| پیش‌فرض          | هیچ‌کدام                                        | `on_track`              |

**مهم**: `risk_status` ذخیره نمی‌شود؛ هر بار محاسبه می‌شود تا داشبورد همیشه با واقعیت هم‌خوان باشد.

### ۳. مجوزها (RBAC)

نقش‌ها در `Member` ذخیره می‌شوند و کلاس‌های DRF در `core/permissions.py` اعمال می‌کنند:

| دسترسی                               | admin     | deputy | team_manager | scrum_master | developer |
| ------------------------------------ | --------- | ------ | ------------ | ------------ | --------- |
| خواندن داشبورد نقش خود               | ✅        | ✅     | ✅           | ✅           | ✅        |
| تغییر **اولویت** پروژه               | ✅        | ✅     | ✅           | ❌           | ❌        |
| تغییر وضعیت/تاریخ اتمام              | ✅        | ❌     | ✅           | ❌           | ❌        |
| ایجاد/ویرایش پروژه                   | ✅        | ❌     | ✅           | ❌           | ❌        |
| ثبت وظیفه/مانع/تیکت/کار ورودی        | ✅        | ✅     | ✅           | ✅           | ✅        |
| تغییر وضعیت وظیفه‌ی **خود**          | —         | —      | —            | —            | ✅        |
| تخصیص وظیفه/تعیین مسئول              | ✅        | ✅     | ✅           | ✅           | ❌        |
| ویرایش تخصیص ظرفیت **خود**           | —         | —      | —            | —            | ✅        |
| گزارش هفتگی + audit + تاریخچه اولویت | ✅        | ✅     | ✅           | ✅           | ❌        |
| تغییر نقش عضو                        | فقط admin |        |              |              |           |

**اصل**: UI فقط نمایشگر مجوزهاست؛ همه‌چیز در View/Serializer با 403 واقعی رد می‌شود
(هر رد شدن به‌طور زنده آزمون‌شده است).

### ۴. وقایع و ردپا

- `core/signals.py` بعد از هر `save` روی موجودیت‌های کلیدی، سطر `AuditLog` می‌زند
  (کننده، عمل، شیء، مقدار قبل/بعد، یادداشت).
- `PriorityChange` یک مدل **جدا و سطح‌بالا** است: old/new priority + **reason** + **impact**
  - changed_by. صفحه‌ی «تاریخچه اولویت‌ها» فقط از همین مدل تغذیه می‌کند.
- `ProjectStatusHistory` تاریخچه‌ی تغییرات وضعیت/اولویت/تاریخ/پیشرفت پروژه را نگه می‌دارد
  (تایم‌لاین در صفحه‌ی پروژه).

### ۵. گزارش هفتگی (serving، نه batch)

`/api/reports/weekly/` در لحظه محاسبه می‌کند:

- وضعیت پروژه‌های فعال + ریسک
- کارهای تکمیل‌شده ۷ روز اخیر به تفکیک نوع
- موانع باز، تیکت‌های پشتیبانی باز/جدید/حل‌شده
- تغییرات اولویت ۷ روز اخیر
- توزیع ظرفیت به تفکیک پروژه

Batch/جدول گزارش **نیست** چون داده در لحظه ارزان محاسبه می‌شود؛ اگر مقیاس بزرگ شد،
کافی است همین سرویس به cache/ری‌استور تبدیل شود.

### ۶. Frontend

- **SPA** با React Router؛ ورودی‌های نقش‌محور (`homeRoute(role)`).
- `api/client.js`: fetch + session cookie + **X-CSRFToken** برای همه‌ی POST/PATCH.
- کامپوننت‌های مشترک در `components/ui.jsx` (Badge، Card، Table، Modal، Timeline).
- ۴ پیشخوان + ۹ صفحه‌ی عملیاتی/گزارشی (13 صفحه).
- تمام متن فارسی، اعداد فارسی (`faNumber`)، تاریخ‌های `faDate/faAgo`.

## امنیت

- **Session + CSRF**: `SESSION_COOKIE_HTTPONLY`، `SESSION_COOKIE_SAMESITE=Lax`،
  `CSRF_COOKIE_HTTPONLY`؛ فرانت‌اند توکن را در `X-CSRFToken` می‌فرستد.
- **HTTPS در پراپ**: `SECURE_PROXY_SSL_HEADER` + `SSL_REDIRECT` از طریق متغیر `HTTPS`.
- **بدون OAuth در ال‌ف**: احراز هویت با user/password؛ اتصال SSO/LDAP برای فاز بعد.
- **خطای نشتی‌ناپذیر**: در Production، `DEBUG=False` و پاسخ خطا عمومی است.

## مقیاس‌پذیری

- همه‌ی endpointهای list **صفحه‌ای** (pagination + `select_related`)‌اند.
- موتور ریسک O(1) در کوئری‌های ساده است؛ برای ۱۰۰+ پروژه بدون مشکل.
- جداسازی آتی: هر app Django مرز واضح دارد؛ مثلاً `dashboards` می‌تواند به سرویس جدا برود
  بدون تغییر مدل‌ها.

## آزمون

- **۷۱ تست** (Django test runner) روی دیتابیس جداگانه:
  - RBAC: هر نقش × هر عمل (رد/قبول)
  - جریان اولویت‌بندی: تغییر + دلیل + ثبت + سابقه + مجوز معاون
  - موتور ریسک: هر سیگنال
  - تبدیل کار ورودی، audit، گزارش هفتگی
- **آزمون زنده**: همه‌ی endpointهای داشبورد + ۶ سناریوی RBAC با curl از طریق Vite proxy.
