# تصمیمات معماری (ADRهای خلاصه)

هر تصمیم: **تصمیم ← چرا ← هزینه/ایف**.

---

## D1 — مونولیت ماژولار به‌جای میکروسرویس

**تصمیم**: یک اپ Django با ۱۰ ماژول (app) مرزدار.

**چرا**:

- مقیاس واقعی: ۱–۳ تیم، زیر ۵۰ کاربر، < ۱۰۰ رقابت/ثانیه. میکروسرویس = هزینه‌ی عملیات
  (استریم، دیپلوی، API بین سرویس) بدون فایده‌ی عملکردی.
- ماژول‌بندی با مرز واضح، امکان جداسازی آتی را حفظ می‌کند (D9).
- یک دیتابیس = transaction اتمیک (مثلاً «تبدیل کار ورودی به پروژه» یک transaction است).

**هزینه**: جداسازی آتی سخت‌تر از میکروسرویس‌های از‌فایل؛ اما در این مقیاس هزینه‌ی
جداسازی < هزینه‌ی نگهداری چند سرویس است.

## D2 — Django + DRF به‌جای FastAPI/Node

**چرا**:

- `BaseModel` + signals + admin رایگان + اکوسیستم بالغ (auth, sessions, CSRF, i18n).
- DRF pagination/permission/serializer دقیقاً با مدل RBAC ما جور است.
- تیم با Python آشناست؛ هزینه‌ی یادگیری صفر.

**هزینه**: هم‌زمانی (async) ضعیف‌تر — در این مقیاس بی‌اهمیت (I/O محلی به PostgreSQL).

## D3 — ریسک «محاسبه‌شده و زنده»، نه ذخیره‌شده

**تصمیم**: `risk_status` ستون ندارد؛ `dashboards/risk.py` در هر درخواست محاسبه می‌کند.

**چرا**:

- ریسک تابع زمان است (مهلت نزدیک‌تر می‌شود؛ مانع رفع می‌شود). ذخیره‌شده = منقضی‌شده.
- شفافیت: هر سه سیگنال (مانع باز / مهلت / به‌روزرسانی ضعیف) قابل نمایش دلیل است.
- هزینه محاسبه ناچیز (کوئری‌های indexشده).

**هزینه**: محاسبه‌ی مکرر؛ اگر روزی پرهزینه شد → cache در لایه سرویس (ساختار همان است).

---

## D4 — تغییر اولویت: «مدیریت با ردپا»

**تصمیم**:

- مجوز: `admin + team_manager + deputy` (طبق تصمیم سازمانی؛ معاون **تصمیم‌گیر** است،
  نه فقط خواننده).
- دلیل (reason) الزامی، اثر (impact) اختیاری — هر دو در `PriorityChange` ذخیره می‌شوند.
- تاریخ اتمام/وضعیت **نمی‌تواند** با اولویت تغییر کند (403 برای deputy)؛ این‌ها
  تصمیم عملیاتی مدیر تیم است.

**چرا**:

- مشکل اصلی مسئله، _تصمیمات بدون ردپا_ است؛ ردپا باید ساختاری باشد نه رفتاری.
- جداسازی «تصمیم اولویت» از «برنامه‌ریزی عملیاتی»، مرز نقش معاون/مدیر تیم را شفاف نگه می‌دارد.
- آزمون‌های زنده تأیید کردند: deputy روی status/date = 403.

**هزینه**: معاون برای اصلاح تاریخ باید با مدیر تیم هماهنگ کند — این هزینه‌ی آگاهانه برای
حفظ مرزهای نقش است.

## D5 — بدون تایم‌شیت: ظرفیت = درصد تخصیص

**تصمیم**: `CapacityAllocation(member, project|support, percent)`؛ هیچ ثبت زمانی وجود ندارد.

**چرا**:

- تایم‌شیت = مقاومت فرهنگی بالا + داده‌ی «نظارتی» که اعتماد می‌شکند.
- سؤال واقعی مدیریت «**کجا** ظرفیت می‌رود؟» است، نه «دقیقاً چند ساعت».
- بیش‌تخصیص (>100٪) به‌جای خطا، **هشدار** است — واقع‌بینانه (انسان‌ها ۱۱۰٪ هم می‌شوند).

**هزینه**: نمی‌توان «هزینه‌ی دقیق پروژه» یا «productivity فرد» محاسبه کرد — آگاهانه رها شد.

## D6 — پشتیبانی = تیکت، نه وظیفه

**تصمیم**: مدل جدا `SupportTicket` (severity + status + started/resolved).

**چرا**:

- پشتیبانی در `work.Task` غرق می‌شد؛ حالا «چند درصد ظرفیت، پشتیبانی است؟»
  با یک کوئری جواب می‌گیرد و در گزارش هفتگی «بار پشتیبانی» دیده می‌شود.
- بدون تایم‌تراکنگ: فقط timestamps شروع/حل.

**هزینه**: دو مدل مشابه (Task/Ticket) — هزینه‌ی شناختی کوچک در برابر شفافیت بزرگ.

## D7 — کار ورودی: «اول ثبت، بعد تصمیم»

**تصمیم**: `IncomingWork` با جریان `new → evaluating → accepted → converted_*`.

**چرا**:

- کار غیربرنامه‌ای امروز در واتس‌اپ می‌میرد؛ ثبت اولیه آن، **شکاف پاسخ‌گویی** را پر می‌کند.
- تبدیل به task/ticket/project، خط تعلق را شفاف می‌کند (کجا از کار ورودی آمد).
- رد (rejected) هم ثبت می‌ماند — شفافیت در «نه گفتن» هم مهم است.

## D8 — گزارش «در لحظه»، نه batch

**تصمیم**: `/api/reports/weekly/` همه‌چیز را آن‌لاین محاسبه می‌کند.

**چرا**: حجم داده کوچک؛ batch + جدول گزارش = هزینه‌ی sync و تعویج.
ساختار سرویس (`dashboards/report.py`) طوری است که بعداً cache/ری‌استور اضافه شود
بدون تغییر API.

## D9 — مرز ماژول‌ها = مرز جداسازی آتی

**تصمیم**: هر app فقط مدل و منطق خود را دارد؛ ارتباط از طریق FK نامدار
(`"projects.Project"`) و سرویس‌های `core`/`dashboards`.

**چرا**: اگر روزی `dashboards` یا `audit` جدا شد، FKها و APIها مرز طبیعی هستند.
**هزینه**: الان هزینه‌ای ندارد (دستورالعمل سبک در کد).

## D10 — احراز هویت: Session + CSRF (ال‌ف)

**تصمیم**: `django.contrib.auth` + session cookie + `X-CSRFToken` از SPA.

**چرا**:

- ساده‌ترین مدل امن برای «اپ داخلی با کاربران شناخته‌شده».
- SPA هم‌منشأ (Vite proxy) → cookie + CSRF دقیقاً کافی است؛ OAuth پیچیدگی بی‌جایی است.
- SSO/LDAP به‌عنوان فاز ۲ (پشت همین auth) قابل اتصال است.

**هزینه**: token/API-key برای کلاینت‌های غیرمریبری نیست (نیاز فعلی وجود ندارد).

## D11 — UI: یک SPA، چهار پیشخوان — نه چهار اپ

**تصمیم**: React Router + `homeRoute(role)`؛ یک کدبیس، داده‌های یکسان، مرز مجوز.

**چرا**:

- داده‌ها مشترک‌اند (پروژه‌ها/موانع/ظرفیت)؛ چهار اپ = چهار بار نگهداری یک داده.
- مجوز در API اعمال می‌شود؛ UI فقط «نشان می‌دهد چه چیزی قابل انجام است».
- یک لایه‌ی CSS/RTL/فارسی برای همه.

**هزینه**: bundle بزرگ‌تر (~75KB gzip) — بی‌اهمیت در این مقیاس.

## D12 — آزمون: RBAC را «آزمایش‌شده» نگه می‌داریم

**تصمیم**: ۷۱ تست؛ هر رد/قبول مجوز به‌صورت صریح تست شده (نه «فقط happy path»).

**چرا**: مجوزِ شکسته = بدتر از نبود مجوز (اعتماد کاذب).
**هزینه**: ۱۷۰ ثانیه اجرای تست — قابل قبول مقابل ریسک امنیتی.
